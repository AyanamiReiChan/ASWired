## 发布策略

先固定一个受支持 Linux/架构/Xray 组合和一个 3X-UI 基线做契约测试，再增加运行环境。每次升级先备份，选一个测试节点发布，运行配置/健康/流量计量回归后分批扩大。数据库变更使用兼容窗口，Agent 新旧版并存。发布失败不回滚金额事实、撤销水位或已确认流量。

外部 Komari 探针固定为 **1.2.5-fix2**，不适用上述 Xray 管理 Agent 的多版本策略。版本未知或不符时显示未验证/不匹配并停止该 Komari 来源同步，不自动升级 Komari、不切到其他供应方；其他版本须另行修改支持范围并完成契约与实机验收。

## 16. 必须通过的验收场景

| 场景 | 通过条件 |
| --- | --- |
| 两用户争最后一个slot | 只一人获得hold；另一方409；capacity不超售 |
| 同用户重复提交订单 | 同幂等键同body得到同订单；不同body409 |
| 付款回调重送10次 | 只一笔付款分录、一次权益和一次quota grant |
| hold过期后付款到达 | 无空slot则PAID_UNALLOCATED；不抢占，不假开通 |
| 100元三人AA | 33.34/33.33/33.33且总额精确100；重复计算排序一致 |
| 中途加入、退出、退款 | 依据冻结策略计算；旧结算不可修改；退款不超可退余额 |
| 多套餐基础+加油包 | 独立grant到期、最早到期优先、不同scope不互借 |
| 手动停用后续费/清零 | 手动原因仍在，不被自动enable复活 |
| 成员越权访问另一席位 | 服务端拒绝或隐藏；无其他凭证、IP、账单泄露 |
| 3X-UI client完整替换 | 未修改字段/凭证/subId/续期参数保持正确 |
| 3X-UI两入站一处失败 | PARTIAL且保存成功集合；重试不重复身份、不多加额度 |
| API超时实际已创建 | 先读回确认，复用凭证，不再创建重复client |
| master与直连同时接管 | ownership校验拒绝；必须先handover |
| 旧命令、重送与乱序 | 对照固定版本的顺序、重试和恢复行为；未取得样本前不以自建owner_epoch协议代替 |
| 3X-UI外部并发修改 | 检测drift并停止冲突发布；不宣称If-Match强保护 |
| Agent执行中断电 | 对照上游启动、配置恢复、补报和升级恢复行为；具体持久化机制以核对结果为准 |
| 配置校验失败与回滚 | 按上游校验、历史配置和回滚行为验收，记录对连接和撤销状态的真实影响 |
| 遥测重复、断网与counter归零 | 对照累计计数、增量上报及恢复修复，核对计量不重复和重启窗口；不虚构消息序号或本地WAL算法 |
| 面板恢复旧数据库 | 对照固定版本恢复后节点、配置和已确认用量，记录差异；不要求未公开的generation协议 |
| 限速与流量超限 | 按上游继承优先级、节点和用户作用域、触发及恢复动作验收，不使用旧lease/BOUNDED/STRICT模型 |
| 连接数达到限制 | 按用户+物理节点汇总；拒绝新连接，既有连接继续；独立核对禁用、到期和吊销行为 |
| Vision限速 | 采用VisionLimiterHook保留splice；不限速路径及受控路径均真实验证 |
| Agent断连、时钟异常、磁盘压力 | 对照上游同版本的断连策略与恢复，未核实项明确记录；不自行增加冷启动租约门槛或两种离线策略 |
| 内嵌与外置模式 | 内嵌核心与Agent同PID、共享生命周期；外置核心独立进程并通过gRPC管理 |
| 节点身份与三种传输 | 独立agent_token、主控公钥和上游加密信道；WS/HTTP/Pull及Auto回退按固定版本实测 |
| Docker与联邦 | Docker按host+embedded运行；联邦owner转发consumer密文且不读取正文，授权边界逐项测试 |
| 全功能无付费墙 | 新部署未配置许可证也能使用全部原PRO功能；不出现付费激活、许可证席位或商业功能锁 |
| 订阅token轮换 | 旧URL停止拉取；若代理凭证未撤销，明确其仍是另一工作流 |
| 每席位独立credential | A退出或泄露轮换不迫使B修改其凭证 |
| 格式不兼容 | 输出明确支持集合；JSON对象/数组、Mihomo等用真实客户端导入验证 |
| 完整恢复演练 | 空白环境恢复业务、密钥、配置、账本与节点映射；支付与配额差异闭合 |
| 原生探针与登录回接 | 无Komari采集/历史/独立部署可用，密码/Passkey回接与注销生效；详见第18份完整验收 |
| Komari 版本锁定 | 只允许 1.2.5-fix2；未知、不匹配、认证失败与连接失败分开显示 |
| Komari 节点结构与绑定 | 多节点 UUID-keyed 字典、单 UUID 对象均正确解析；重命名后绑定不变，未绑定节点不公开 |
| Komari 缺字段/断连 | 缺失值显示未知，旧数据标采样时间与过期；不把连接失败冒充所有节点离线 |
| Komari 公开范围变更 | 服务器和字段白名单严格生效，撤回后缓存失效；无管理地址、凭据、成员数据泄露 |
| Komari 与计量分离 | 主机网卡流量不进入成员账单或配额消费；探针故障不触发配置接管或额度调整 |



## 17. 实施顺序与完成标准

### 第一阶段：可演示、可接入、业务不丢

完成组织权限、服务器库存、3X-UI只读导入、计划版本、拼车slot/hold、订单与人工付款核销、AA预览、金额账本、独立订阅、操作中心。演示可以先用样例连接，但读模型与真实API契约一致；付款按钮不能直接把provider_payment标成功。

### 第二阶段：可靠交付与运营

完成v3.8.0适配、Outbox/inbox、单backend串行队列、完整字段读写、partial/nodePending、权益与多套餐规则、上游计量和配额行为、凭证轮换、告警、备份恢复。以两个隔离面板和至少两种核心协议完成失败注入测试后再开放真实业务。

### 第三阶段：原生Agent与完整运行时

按第13、16、17份文档实现节点Token、主控公钥及上游加密信道，支持WS/HTTP/Pull/Auto、同进程内嵌核心和外置gRPC核心、VisionLimiterHook、原生探针、原生安装及Docker host部署。配置下发、历史、回滚、升级与恢复先形成固定版本样本，再实现与验收；保留3X-UI适配。

### 第四阶段：全功能对照与部署验收

覆盖全部原PRO功能，包括限速、限连接、探针独立部署和登录回接、联邦等。核对协议与核心分支、密文转发和计量恢复的未公开细节；缺少基线证据的项目保持待验证，不能用自拟机制标记完成。执行168项对照及无许可证全功能测试，全部通过后才宣称对应范围对齐。

**交付完成标准：** 可从管理员建节点/建组/建套餐开始，经成员抢位付款、独立凭据交付、消费统计、AA结算、续费/退款/退出，完整走通并具备失败恢复；每一处UI“完成/已停用/已退款/已恢复”都有后端事实和可追溯回执支持。
